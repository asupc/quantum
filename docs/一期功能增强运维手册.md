# 一期功能增强运维手册

> 适用范围：`docs/功能增强分期实施计划.md` 的一期 G1~G4 与独立交付包 G-Push。
> 接口与字段口径一律以 `docs/执行记录与外部推送API契约.md` 为准，本手册只写**操作流程**。
> 编制日期：2026-09-26。

## 0. 动手前先确认的三件事

1. **单实例前提**：调度与重试领取都假设只有一个 Quantum.API 实例在跑（Quartz 内存态重建，无跨节点选主）。
   扩到多副本前必须先补独立选主/持久调度设计，否则同一任务会被多节点各跑一次。
2. **生产库是哪一个**：`appsettings.json` 的 `DBType` 决定生效的 DbContext（MySql → `nas…:5798/quantum`；Sqlite → `db/<DBAddress>`）。
   迁移会在**应用启动时自动执行**（`DbInitializer.Initialize`），所以「启动服务」等于「改库结构」，必须先备份。
3. **本次带的都是加法式变更**：4 张运行/告警表 + 2 张外部推送表 + `t_chat_session.DisplayTitle` + `t_chat_message.SessionTitle`。
   没有列删除、没有数据回填。**事故回退时不要执行 Down**（会连新表与历史一起删）。

## 1. 升级前备份（必做，不可跳）

```bash
# SQLite：在线备份 API（不要直接 cp 正在写的库文件）
sqlite3 db/<DBAddress> ".backup '<备份目录>/quantum-$(date +%F-%H%M).db'"

# MySQL：一致性导出（--single-transaction 取 InnoDB 快照，不锁表）
mysqldump -h <host> -P <port> -u root -p --single-transaction --routines --triggers \
  --databases quantum > quantum-$(date +%F-%H%M).sql
```

还要一起备份的（脚本与配置都在库里之外）：

- `Quantum.API/Quantum.Web/scripts/quantum/`（任务源码 + `t_script_version` 之外的当前文件态）
- `appsettings.json`（含真实连接串与密钥，**不外传、不入日志、不进新文档**）
- 安卓发布用 keystore（仓库外，经 `quantum-app/keystore.properties` 注入；丢失即无法端内自更新）

**恢复演练**：把备份还原到隔离目录并能正常启动一次，再认定备份有效。没演练过的备份按没有备份处理。

## 2. 迁移执行（发布日）

1. 生成/核对迁移（本仓库固定双 DbContext，须各出一份）：

   ```bash
   CreateMigration.bat <迁移名>
   ```

   产物分落 `Migrations/SqliteMigrations/` 与 `Migrations/MySqlMigrations/`。

2. **人工审查两份 Up/Down**：表名/列型/默认值/索引逐条对照，特别核 `Up` 里有什么、`Down` 是否对称。
   两侧模型差异（如 `nvarchar(n)` 与 `varchar(n)`、索引键长）是 MySQL 侧最容易翻车的地方。

3. 停服务 → 备份（§1）→ 换二进制 → 启动，启动日志关注两类输出：
   - `挂起迁移应用失败，库结构未更新` → **严重**：应用会带旧结构继续跑（表现为 Unknown column / 写入失败）。
     按维护窗口恢复备份重来，不要绕过 `DbInitializer` 带病启动。
   - `检测到 EnsureCreated 存量库（无迁移历史），已回填全部迁移为已应用` → 预期行为（早年老库无迁移历史）。

4. 结构确认（一次性）：

   ```sql
   select table_name from information_schema.tables
    where table_schema = database()
      and table_name in ('t_task_run','t_task_failure_policy','t_task_alert_state','t_task_alert_event',
                         't_external_push_credential','t_external_push_request');   -- 应为 6
   select column_name from information_schema.columns
    where table_schema = database() and column_name in ('DisplayTitle','SessionTitle');  -- 应为 2
   ```

   SQLite 侧改用 `sqlite_master`。已在本地一次性 MySQL 8.4 容器验证过全链 Up / Down 回 Init / 旧库增量三条路径（见契约文档 §7.1）。

## 3. 上线顺序与灰度（扩展式，不做大爆炸）

新增表/字段 → 后端（兼容旧 API）→ Web → App → 按任务灰度开能力。

| 阶段 | 动作 | 回退动作（都是关开关，不动数据） |
|---|---|---|
| 1 | 后端发布。运行记录采集默认开启；重试/告警/外部凭据**全部默认关闭** | 退回旧后端，新表留着不影响旧代码 |
| 2 | Web 发布（执行记录抽屉、失败策略侧栏、外部推送接入页） | 退回旧 Web；新端点没人调即可 |
| 3 | App 发布（最近执行 + 详情 + 告警深链）；旧版忽略新增可选字段 | 停推新版；服务端返回的可选字段本就向后兼容 |
| 4 | 挑 1~2 个**幂等**任务开 `Enabled` + `RetryCount=1` 观察 | 关 `Enabled`（会立即作废该任务待重试排程） |
| 5 | 外部推送：先只给测试接入方建凭据并启用 | 禁用凭据即停止新投递，已存通知/会话消息保留 |

灰度期间盯这几项（任一异常就停灰度并回退）：

- `t_task_run` 里长期挂 `Running` 的记录数（启动恢复会把超宽限的判为 `Interrupted`，残留说明有实例没正常收尾）
- 待重试堆积：`select count(*) from t_task_run where Status=3 and NextAttemptAtUtc is not null;`
- 告警投递失败：`t_task_alert_event` 中 `DeliveryStatus=2`（Failed）且 `DeliveryAttempts` 逼近 5 的行
- `logs/` 与 `t_task_run`、`t_external_push_request` 的磁盘增长速率

## 4. 日常运维动作

**容量与清理**：执行记录默认保留 90 天，由后台每 6 小时批量限速清理（一批 500）。清理**不碰**运行中/待重试记录、不删脚本版本、不改现有日志清理行为。事件记录保留不短于执行记录。要改保留期改 `QuantumRuntimeOptions.RunRetentionDays`。

**任务删除/禁用**：历史执行记录**故意保留**（`TaskId` 不做级联删除），删除会同时作废该任务的待重试排程。任务删除后的历史仍可读，靠的是运行行里的名称与脚本快照。

**凭据运维**（G-Push）：
- 明文密钥只在创建/轮换那一次显示，平台只存 SHA-256 摘要。**丢了只能轮换，找不回来。**
- 疑似泄露：立刻「禁用」再轮换（禁用即停止新投递，不抹已存消息）。
- 列表、日志、错误文案都不含密钥，也不含完整 `Authorization`；网关/代理日志需屏蔽该头。
- 强制 HTTPS 或可信代理 TLS；生产 CORS 不为第三方放宽。
- 首次启用前跑一次前缀冲突检查：确认没有任务/会话键占用 `external:` 前缀（启动时会自动扫描并以 ERROR 留痕，有冲突先迁移再启用凭据）。

**排障入口**：某次执行为什么失败 → Web 任务页「执行记录」→ 详情看尝试时间轴与 `SafeSummary` → 「查看实时日志」跳受限日志详情。
库里只有截断脱敏摘要，完整堆栈只在受权限控制的日志文件里；不要把堆栈原文贴进对外渠道。

## 5. 发布后回归清单（G5 门禁）

```bash
dotnet test                                                   # 后端全绿（含迁移链、鉴权隔离）
cd quantum-web && npm run test && npm run build               # 前端单测 + 产物
cd quantum-app && ./gradlew testDebugUnitTest assembleDebug    # App 单测 + 可安装包
```

手工冒烟（需登录凭据与真实设备/浏览器，本轮环境不具备）：Web 执行记录抽屉与策略保存、App 最近执行与告警深链、
第三方 curl 推送在线/离线两态与重复 `Idempotency-Key` 重放、旧版 App 收含新字段通知的降级表现。

## 6. 明确不要在事故中做的事

- 不要 `Down` 迁移删新表/新列（历史与幂等记录会一起没了）。
- 不要手改 `t_task_alert_state` 的计数来「消掉」告警——去重键在 `t_task_alert_event`，改状态会造成下次该告不告。
- 不要为了恢复快而绕过 `DbInitializer` 启动。
- 不要在多副本下开自动重试。
- 不要为了让通知栏好看而把富文本原样投给 OS 摘要（必须剥成纯文本）。
