## 0. 决策摘要与前置条件

- **先修结果口径，再谈自动重试**：`TaskExcuteService.Run/ExecTask` 的脚本路径非法、文件不存在、门禁或编译失败等分支写日志后直接返回；脚本异常/取消也被捕获只记日志，`TaskService.RunSingleTaskAsync` 的异常处理不一定可达；日志创建时 `Success=true`。`MessageProcess` 甚至可能在脚本失败后发送“任务完成”文案。因此第一期第一块是可信的终态传播，而不是先加重试按钮。
- **已有能力不重复建设**：保留 `TaskService` 任务导入导出、`LogsService` 实时日志、`ScriptVersionService`、`AppPushService` 的通知+会话镜像、`AgentAutoAnalyze` 默认关闭的失败分析以及 App 全局通知偏好。新记录不是替换已有日志，而是建立可索引的“单次执行/尝试”实体并关联日志。
- **部署模型**：第一期以**单实例调度服务**为约束；Quartz 目前由托管服务提供，任务调度以内存状态重建。多实例抢占/分布式锁不是本期承诺；部署文档写明不得横向扩容调度节点。若实际有多实例，先补独立选主/持久调度设计再启用自动重试。
- **本地缺失文档**：当前检出没有 `docs/`，尽管仓库指引要求修改前阅读 `docs/security/公网部署安全审计-2026-09-14.md`、`docs/App端API契约.md`、AI 计划文档。**开始实施前必须找回并核对这些文件**；拿不到时暂停相关敏感区域和 App 契约改动，不能以本文替代原始契约。本文件新建于 `docs/` 不代表历史文档已恢复。
- 开工前固定基线：实际运行 `dotnet test`、`quantum-web` 的 `npm run test` 和 `npm run build`；记录既有失败、DBType、存量数据量、App/服务版本。计划估算不等于已验证的基线。

## 1. 目标、边界和成功标准

目标：让每次执行**可识别、可追踪、可区分成功/失败/取消**；失败可按显式配置做安全的有限重试，最终失败和恢复可按规则发送不刷屏的通知；Web/App 能直达对应执行与日志。独立的 G-Push 允许第三方用专属授权 API 发送受限富文本通知，并指定独立的会话标题；不得借此获得指令或管理权限。

不做：改造 `.cs` 脚本门禁/运行权限、声称强制杀死不响应取消的进程内脚本、默认启用重试、默认向 AI 发送错误明文、后台推送厂商通道、跨节点精确一次执行、把既有 `ResultModel` 改为裸 HTTP 错误、对旧日志猜测真实执行结果、在第一期做 DAG/跨数据库一键恢复。

一期验收：新执行 100% 有稳定 `RunId` 和确定的终态或明确的“中断/未知”；脚本异常、文件缺失、编译/门禁失败均不被记成成功；未配置策略的存量任务仍只运行一次；显式配置重试才最多增加 N 次，每次可见且不会越过次数上限；告警阈值/恢复通知去重可验证；非 Manager 不可读 Manager 任务及其执行详情，匿名/临时令牌不可获取管理员能力。

## 3. 一期：执行结果、运行记录、失败策略和告警

### 3.1 执行结果契约（先落地，不改既有脚本接口）

1. 在 Application 定义内部 `TaskExecutionResult`：`Outcome={Succeeded, Failed, Rejected, Canceled, Interrupted}`、受控 `FailureCode`、SafeSummary、时间、关联 LogId/日志定位信息。**只在真正结束后给终态**。非法路径、文件丢失、门禁拒绝、编译失败、加载失败归 `Rejected`；脚本抛异常归 `Failed`；协作取消生效归 `Canceled`；进程重启时残留运行归 `Interrupted`。脚本收到取消仍正常返回，标 `Canceled`，不误报成功；不响应取消的仍保持 Running，不能宣称被杀死。
2. 改造 `TaskExcuteService.Run/ExecTask` 向调用者返回结果（或新内部入口包裹它），保留原有日志文本与实时尾览；**逐条检查全部早退和 catch**，避免靠解析字符串推断。`AgentTestRunService` 改消费结构化结果，并保持影子目录清理及脚本安全检查；不能引入双套结论。`MessageProcess` 成功完成文案只在结果成功时发送；`OpenTriggerTaskService` 同样记录真实结果。新执行日志 `Success` 与终态一致；旧日志不反填“成功/失败”。
3. 错误信息分层：数据库/通知仅存有限长度、不含环境变量/令牌/完整请求体的安全摘要和错误码；详细异常仅保留在受权限控制的日志链路（现有日志本就可能含脚本输出，需复核脱敏策略）；不把脚本异常堆栈作为 AI 输入或推送正文。脚本门禁、`SafeFile`、ManagerOnly 白名单原样保留。

### 3.2 单次运行与重试的数据模型

拟新增 `t_task_run`（每次尝试一行），至少包含 `Id(RunId)`、`RootRunId`、`Attempt(1..N)`、`TaskId(nullable)`、`TaskNameSnapshot`、`ScriptFileSnapshot`、`ScriptHashSnapshot(nullable)`、`TriggerSource(Manual/Cron/Command/OpenTrigger/Shadow)`、`TriggerRef(脱敏 ID)`、`Status(Pending/Running/Succeeded/Failed/Rejected/Canceled/Interrupted)`、`FailureCode`、`SafeSummary`、`StartedAtUtc`、`FinishedAtUtc`、`NextAttemptAtUtc`、`LogId(nullable)`、`CreatedAtUtc`。`TaskId` 不做级联删除；索引 `(TaskId,CreatedAtUtc)`、`(RootRunId,Attempt)` 唯一、`(Status,NextAttemptAtUtc)`；入库前限定字符串长度。`LogId` 只存受限日志行 Id；日志被清理时详情显示“日志已清理”，不拼接任意路径。

拟新增 `t_task_failure_policy`：`TaskId` 主键、`RetryCount`（0~3，默认 0）、`BackoffSeconds`（30~3600，默认 60）、`AlertAfterConsecutiveFailures`（1~10，默认 1）、`SendRecovery`（默认关闭）、`CooldownMinutes`（0~1440，默认 60）、`Enabled`（默认关闭）。权限：修改策略只允许正向 Manager claim；非 Manager 可查看自己可见任务的执行记录但不读策略内部路由；禁用/删除任务时立即取消后续待重试。所有策略上限服务端校验，UI 仅辅助。

在 `Quantum.Entities/Model` 与 `Quantum.Data/IQuantumDbContext.cs`、SQLite/MySQL 两个 DbContext、`QuantumModelConfiguration.cs` 加入模型和索引，**两个数据库分别生成迁移**，对照 Up/Down/唯一约束/默认值/索引；`TaskSaveModel` 不直接绑定内部运行字段，策略独立 DTO。`DbInitializer` 的 `EnsureCreated`/迁移历史兼容用新库、旧库两条路径测试；不能用 EnsureCreated 代替增量迁移。

### 3.3 入口收口、状态流和重试调度

- 先做入口矩阵：`TaskController.ExecTask`、`TaskJob`、`MessageProcess`、`OpenTriggerTaskService`、`AgentTestRunService`、子步骤以及现有直接调用 `Run` 的路径；每条路径明确 `TriggerSource`、任务身份、权限、日志、是否允许重试。**第一期自动重试只作用于有持久任务 Id 的手动/Cron 执行，默认关闭**；指令/外触/影子只记录结果，待二期单独评估其输入重放与副作用风险。
- 请求受理先写 `Pending` 并返回 RunId（批量执行返回每项 TaskId/RunId）；后台尝试用数据库条件更新把 Pending 领取为 Running；结果落终态（事务性状态 CAS + 唯一 `(RootRunId,Attempt)` 防重复）。手动接口升级响应需核对 Web/App 现有 `bool` 调用方并做兼容：过渡期保留原端点行为，新设 `POST api/Task/execute-runs` 返回 RunIds；旧端点内部复用新执行服务，但仍返回原有 bool，待客户端迁移完成再讨论移除。绝不改已有成功信封语义。
- 重试仅在 `Failed`（脚本异常）且任务启用、显式 opt-in、次数未到上限时调度；`Rejected/Canceled/Interrupted` 默认不重试。固定指数退避上限 3600s，具体 `NextAttemptAtUtc` 持久化，延迟触发由托管后台轮询领取到期记录（例如 5~15s，启动后恢复）；统一复用现有并发闸，并给**同一任务跨入口互斥或明确跳过**策略，禁止重试与手动执行互相重入。后台异常要可观测；定时停机时不能把非响应脚本写成已取消。
- 重试期间任务/脚本可能变化：尝试领取前核验任务仍启用且权限未变；原则上使用本次根执行开始时脚本版本快照进行重放，若无法安全保留经门禁编译的源码快照，则**第一期先限制“脚本变更后取消重试”**并记录原因；绝不能悄悄执行另一版本。外部副作用无法事务回滚，页面和帮助文本必须标“仅适合幂等脚本”，首次默认不自动重试。任务删除、脚本删除、服务重启时 pending 状态的处理要有测试。
- 进程启动恢复：扫描超过宽限期的 Running 标 Interrupted；Pending 的后续尝试按到期继续领取；不能对已实际运行但未写完终态的尝试无条件重放。数据库写失败时执行结果不得默默当成功，记系统错误并停用该条自动重试；每个状态更新采用小事务，含异常与重启注入测试。

### 3.4 通知规则与 AI 分析时点

- 在 `TaskFailurePolicyService`/`TaskAlertService` 中计算**连续最终失败**（同一 RootRunId 的多次尝试只计一次），达到阈值时创建事件 `FailureOpened`；成功且此前处于打开状态才 `Recovered`。相同事件以 `(TaskId,AlertType,RootRunId)` 唯一键去重；冷却期内聚合计数不重复投递，冷却后仍失败才可摘要提醒；禁用任务不会制造“恢复”事件。
- 告警状态用单独持久表 `t_task_alert_state`（TaskId、ConsecutiveFailures、Open、LastSentAtUtc、LastFinalRunId）和 `t_task_alert_event`（Id、TaskId、RootRunId、Type、CreatedAtUtc、DeliveryStatus）；事务内写事件与状态，后台按事件幂等投递并记录失败/重试。**不承诺 WS 网络传输 exactly-once**，依赖既有 MsgId 做客户端去重；须评估保存通知成功而状态回写失败时的重投风险，必要时以 EventId 作为消息幂等键扩展 `AppPushService`，不能仅在内存打标。
- 通知投递继续走 `AppPushService`（含会话镜像），App 原有全局 DND/分类仅影响本地弹出，服务端规则决定是否生成消息；Web/App 查看仍可追溯。Manager 任务的告警/日志只供管理员，不能复用现有广播方式向非 Manager 披露日志详情。`AgentAutoAnalyze` 移到**最后一次确定失败后**，且维持全局开关，自动分析不会因每次尝试重复触发；写权限快照/高危提案仍遵原机制。

### 3.6 保留、清理和容量

- 执行记录保留 90 天可配（默认值需在实施前结合数据量确定）、事件记录保留不少于执行记录；清理采用批量限速和可审计日志，不删除正在运行/待重试的数据，不删除脚本版本，也不改变现有日志清理行为。缺少日志文件只显示安全占位。列表分页上限和 `(TaskId,CreatedAtUtc)` 索引是必须项；大数据量压测 SQLite/MySQL 各一次。
- 所有时间后端持久化 UTC，界面按客户端时区显示；Cron 调度时区与 Run 时间区分。日志、告警、统计量命名不可把“HTTP 受理成功”等同于“脚本成功”。

### 3.7 独立交付包 G-Push：第三方授权富文本消息推送 API（不依赖 G1~G4）

**目标与语义**：受信任的外部系统调用 `POST api/ExternalPush/messages`，向当前管理员设备发送一条可带**受限富文本标记**的通知，并可为该消息**指定会话标题**；标题相同（同接入方内）进入同一会话，标题不同进入不同会话。服务端同事务持久化通知、会话镜像和会话标题；在线通过现有 WS `notify` 帧投递，离线靠现有 REST 增量补拉，不承诺厂商离线唤醒、设备已展示或已读。成功响应仅表示**通知与会话消息已持久化**（返回 `NotificationId/MsgId/SessionKey`，不返回凭据）；WS 或提交后的“送达状态更新”失败只留痕，不能改写已经提交的成功结果，客户端仍可补拉。第三方不能通过本端点执行指令、脚本或管理操作。首版限单条**文本及项目现有富文本标记**，不支持原始 HTML/任意 Markdown、图片/附件、富交互 `Payload`、自定义 `jump`、指定接收用户、访问 AI 工具或触发任务。

**现有链路和权限隔离**：`OpenController.AuthByBody`/`OpenAuthService.Auth` 以全局 AppKey 签发 10 分钟 JWT，只有 `Name/IP` 等 claim，**没有 push 专属 scope**；普通 `[CustomAuthorizationFilter]` 只验 JWT，不能把它限定为“仅推送”。`NotifiyController.Send` 是 `[ManagerOnly]`，`NotifyService.Send` 走消息处理管道；`AppMessageService.SubmitCommandAsync` 会将消息投入指令队列，第三方推送**严禁复用**。复用并改造 `AppPushService.SendNotificationAsync` 的通知+会话镜像事务、`MsgId/Seq` 与 WS/REST 补拉链路；`category=system`，继续遵守 App 系统通知免打扰。`ChatSessionModel` 目前只有 `SessionKey`、读水位和时间，没有显示标题；Web `sessionTitle` 与 App `ConversationListViewModel.titleOf` 都是用任务名或原始会话键计算标题。`NotifyCard.vue` 和 App 通知卡都直接显示正文，**不会渲染现有普通聊天气泡的富文本**，因此不能仅改请求 DTO 就宣称两端支持。

**受限富文本契约**：`Content` 沿用 `quantum-web/src/utils/richText.js`、`quantum-app/core/common/RichText.kt`、`Quantum.Plugins.QuantumText` 的语法：`{{red|文字}}` 等六色强调、`{{tag:orange|文字}}` 胶囊标签、`{{link:详情|https://example.com}}` 命名链接，允许换行和普通文字；单条最多 50 个有效标记。**不是 HTML/Markdown 输入**；`<script>` 等字面内容必须作为文字安全显示，不能进入 `v-html` 未转义支路。服务端校验有效命名链接 URL 为绝对 `https://`（如需 `http://` 单独审批）、无 userinfo/控制字符，拒绝 `javascript:`、`data:`、`intent:` 等协议；对不支持的/格式不完整的标记统一按字面显示或拒绝（正式契约选定一种且两端一致），避免客户端解析差异。Web `NotifyCard.vue` 改用复核后的受控富文本片段渲染，App 通知卡改用 `RichMessageText`（折叠不影响标题）；Web `RichText.vue` 目前通过 `v-html` 拼接链接，且 App 富文本解析器的 URL 判断与 Web 不完全相同，接入外部可控文本前须补严格链接校验/HTML 转义的双端安全测试。系统通知栏、会话列表摘要、日志与搜索展示**剥离标记只用纯文本**，不把富文本当可执行代码、HTML 或可触发指令的入站消息。

**会话标题的持久化与唯一归属**：请求体 `SessionTitle` 可选；缺省取接入凭据的展示名称，传入时 trim + Unicode NFC 归一化、长度 1~80、禁止控制字符/换行和前后空白、按大小写敏感的**归一化精确值**分组，不允许请求体传 `SessionKey`。服务端基于 `CredentialId` + 归一化标题确定**稳定、不含明文标题**的命名空间会话键（例如 `external:<凭据ID>:<SHA256(归一化标题)>`，长度符合 `SessionKey` 列限制），不同接入方同名标题绝不混会话；同接入方改标题=新会话，**不隐式改名或搬迁旧消息**。固定保留 `external:` 前缀给外部会话：上线前扫描现存任务 Id/`TaskModel.SessionName`、消息与会话键的冲突；若有冲突先安全迁移或调整命名空间，不能覆盖/合并存量；任务新增/修改/导入和其他可写会话键入口必须禁止后续占用该前缀。`ChatSessionModel` 增 `DisplayTitle(nullable)`，外部会话同时写展示名，原会话为 null 保持原有任务名/默认名规则；`ChatMessageModel` 增 `SessionTitleSnapshot(nullable)`，新消息在同一事务写快照以支持**离线仅消息增量补拉**。`ChatSessionOverview`、WebSocket `notify` 帧按**可选** `SessionTitle` 返回，Web/App 优先使用外部会话展示名并本地缓存（App 离线、重启仍应显示标题），旧客户端忽略未知字段仍能收到消息但可能短暂显示 opaque key；客户端版本门槛/灰度顺序需在部署前验证。`Notification.Title` 是**单条通知标题**，`SessionTitle` 是**会话标题**，两者独立且不得互换。

**鉴权与管理**：新增 `ExternalPushCredential`（`t_external_push_credential`）：`Id`（公开标识）、展示名、启用、密钥摘要、创建/最后使用/过期/吊销时间、每分钟配额、备注；Manager 管理端 `ExternalPushCredentialController` `[CustomAuthorizationFilter][ManagerOnly]` 提供创建/列表元数据/轮换/禁用/删除和操作审计。密钥由密码学安全随机数生成（至少 256 位），创建/轮换后只回显一次，只保存高熵密钥的 SHA-256 摘要、固定时间比较，列表/日志/错误绝不返回密钥或完整 Authorization。端点及新凭据默认**关闭**；旧 `Open` AppKey、JWT（包括 Manager JWT）、OpenTrigger secret 无推送权限。`ExternalPushController` 不标 `[AllowAnonymous]`，挂专用鉴权过滤器/策略，仅解析 `Authorization: PushKey <id>.<secret>`，校验状态、有效期、`push:send` 专属 scope；此凭据不能用作项目 JWT，也绝不构造 `Manager=true` claim。无凭据、错误/吊销/过期密钥均返回 HTTP 200 + `ResultModel.Code=401`，不区分 ID 是否存在。管理控制器和发送控制器分离。

**API 契约（V1 草案，恢复 App 契约后确认）**：`POST /api/ExternalPush/messages`；头 `Authorization: PushKey <id>.<secret>`、`Idempotency-Key: <8~128 字符 ASCII 可打印且无空白>`；请求体示例 `{ "Title": "设备告警", "SessionTitle": "机房监控", "Content": "{{tag:red|紧急}} 温度过高\n{{link:查看详情|https://example.com/status}}" }`。`Title` 必填、trim 后 ≤100 且不含 CR/LF；`Content` 必填、≤4096 字符；`SessionTitle` 可选、非空时 1~80 字符，JSON 整体 ≤8 KiB（实际 UTF-8 字节计）；服务端不接受客户端指定来源/会话键/分类/跳转地址。返回 HTTP 200 信封，成功 Data `{ "NotificationId": "...", "MsgId": "...", "SessionKey": "...", "Duplicate": false|true }`；相同接入方+幂等键+**同一归一化 Title/SessionTitle/Content** 重试返回相同 ID 和 SessionKey，不再广播/新增会话；同键不同内容、配额超限、无效参数经 `BusinessException` 返回 Code=500（安全文案），鉴权失败 Code=401。第三方必须判断信封 `Code`，不把 200 当成设备已收到；提供脱敏 curl 示例，文档只使用占位密钥。标题/正文/会话标题均不得记录原文到请求/错误日志。

**持久化幂等与原子性**：新增 `t_external_push_request`（`Id`、`CredentialId`、`IdempotencyKey`、请求摘要、`NotificationId`、`MsgId`、`SessionKey`、`CreatedAtUtc`），唯一键 `(CredentialId,IdempotencyKey)`，设计保留不少于 72 小时；**幂等记录实际删除前始终按旧请求处理**，清理完成后同键再来视新请求，避免“名义 72 小时过期但唯一索引仍占用”的竞态，并在 API 契约写明。`t_external_push_request` + `t_app_notification` + `t_chat_message` + `t_chat_session.DisplayTitle` 的新建/更新在**同一事务**提交；现有 `AppPushService.SaveNotificationWithMirrorAsync` 自开事务，必须重构内部扩展点而不是外层盲目套事务；保留其他通知调用方行为。并发唯一键冲突后回滚/重查：同内容回相同结果、异内容拒绝。提交之后才广播 WS；在线发送后 `AppPushService` 当前还会调用 `MarkDeliveredAsync(msgId)`，这个**提交后的步骤失败也必须 best-effort 留痕**，不能让已入库请求返回失败；原键重试返回同一结果、不会重复广播。批量清理幂等记录不得删除会话/通知历史；不记请求明文或密钥。凭据吊销停止新投递，但不抹已存消息。

**滥用防护与运维**：按凭据限速（默认 60 次/分钟、每日 1000 次）和全局上限及总请求体闸；无效凭据按来源 IP 限制，`KnownProxies`/ForwardedHeaders 未核对前不信 XFF，也不只靠 IP。配额计数失败时不放行；日志只记接入 ID、结果码、时间、字节数，**不记密钥/请求体/完整 URL**。强制 HTTPS 或可信代理 TLS，代理日志屏蔽 Authorization；凭据丢失立刻禁用/轮换。并发限额需原子计数/锁或持久计数；跨实例部署前另定跨节点限流。CORS 生产策略不为第三方放宽。管理端新增“外部推送接入”页，一次性复制凭据、轮换/禁用及调用统计；可预览会话标题和富文本格式，但不提供查看历史明文密钥。

**落点、迁移与测试**：`Quantum.Entities/Model` 增凭据/幂等实体，在 `ChatSessionModel` 增展示标题，在 `ChatMessageModel` 增标题快照，`ChatSessionOverview` 加可选标题；`Quantum.Data/IQuantumDbContext`、SQLite/MySQL DbContext、`QuantumModelConfiguration` 增 DbSet/索引并各自生成**Up/Down 双库迁移**，存量标题列默认 null（不重命名旧会话）。`Quantum.Application` 新增 `ExternalPushService/CredentialService`，改 `AppPushService` 同事务扩展和 `AppMessageService.AppendNoSaveAsync/SessionsAsync` 可选标题接线；`Quantum.Web/Controllers` 新增发送和管理端点，`Startup` 配 DI/限流，notify WS 帧新增可选 `SessionTitle`；Web 更新通知卡/会话标题映射与管理页，App 更新通知卡/OS 通知摘要、本地会话标题存储及网络 DTO（PascalCase 按既有序列化约定）；`quantum-app/core/storage` 的 Room 本地 `ChatSessionEntity`/DAO 需升级版本并为本次版本提供**显式非破坏性迁移**（现有 `fallbackToDestructiveMigration` 会清除离线待发 outbox/选项状态，不能当此次变更的默认迁移方案）；升级前后验证增量补拉、标题快照恢复、未读水位与未发送消息保持不丢，更新第三方 API 和 App API 契约。测试：授权隔离、同键并发/不同标题、标送达失败、会话前缀冲突、标题 NFC/大小写/换行、失联补拉+冷启动还原标题、富文本色标/链接/不完整标记/`<script>`/`javascript:`/超长限制、Web XSS 与 Android 链接行为；全量 `dotnet test`、Web vitest/build、App Debug 单测+真机、SQLite/MySQL 新库/升级双路径必须通过。

**发布与回退**：先恢复项目缺失安全审计及 App API 文档、审计旧 `external:` 前缀冲突；双库迁移和后端以**默认关闭**发布，再发布可显示 `SessionTitle` 的 Web/App（App 旧版忽略可选字段，兼容性需真机验证），最后只给测试接入方启用凭据。验收在线通知/离线补拉、富文本 Web/App/OS 退化、同名标题归组和不同接入方隔离、吊销与幂等；回退先关凭据和请求、保留新表/列与消息，不在事故中直接 Down 丢历史。估时约 9~15 人日（增加双端渲染、标题持久化与双库迁移验证），**独立于 G0~G5 的 15~25 人日**；一期旧审查的日志权限/失败告警阻塞不因本功能解决。
## 4. 后续分期（每期实施前另写细化设计并确认）

### 二期 A：完整备份/恢复（预计 6~10 人日，不和一期混发布）

以只读盘点/导出起步：数据库快照、`scripts/quantum/` 脚本及版本、必要配置清单；生成带 SHA256、格式版本、条目数量的清单，默认**不含 env 值、连接串、JWT 密钥、keystore、日志**。SQLite 使用一致性备份 API/事务快照，MySQL 采用受支持的一致性导出方案，不能简单复制正在写的数据库文件。恢复仅离线维护模式，先验签/校验体积、格式、路径穿越及脚本门禁，在隔离目录演练后原子替换；服务关闭写入与调度，双数据库分别演练恢复成功/失败回滚。是否提供“含密钥的加密备份”由所有者单独确认密钥托管、轮换、下载保护和审计设计，未确认不得做。

### 二期 B：模板库与调度预览（各预计 3~5 人日）

模板只来自受信任、版本锁定的仓库内 `.cs` 模板+元数据，展示所需环境变量名，不带私有值；安装时通过现有 Save 流水线/门禁/编译和版本记录，禁止模板绕过扩展名与 SafeFile。Cron 预览用与 `JobHelper` 同一 Quartz 表达式/时区语义，显示未来 5 次执行、DST 与 misfire 说明；实施前明确默认调度时区（目前代码未显式指定）及升级对老 Cron 的影响，避免“预览”和实际调度不一致。

### 三期：依赖链/编排（预计 10~20 人日，必须单独架构评审）

先支持有限的 A 成功→B / A 失败→C，再评估 DAG 编辑器；设计需包含环检测、版本快照、幂等、失败传播、权限向下传递、取消/补偿、并发与历史展示，严禁利用依赖关系触发无权的 Manager 任务。不开通未经审查的跨任务隐式脚本写权限。该阶段依赖一期运行记录/稳定终态；未完成一期不得直接开发。
