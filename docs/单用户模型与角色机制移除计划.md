# 单用户模型与角色机制移除计划

> 状态：已实施并完成代码、双库与本地端到端验证；生产备份演练及物理设备验收待现场执行。
> 2026-09-29 现状核实：产品已是同一组 `Quantum:UserName/PassWord` 供 Web/App 登录，但代码仍用 `Manager` 作为任务可见性、管理端点和改密吊销依据。用户明确要求产品不再有管理员/普通用户区分。

## 1. 目标与边界

- 只有一个登录账号，可在 Web 和 App 完成现有全部登录后操作；任务没有角色属性，界面不显示角色或“仅管理员”提示。
- 仍区分**登录身份与外部凭据**：Open AppKey、外部推送 PushKey、外触 Secret、通道回调等不能据此取得脚本编辑、系统配置、日志、AI 写入、设备管理等登录操作能力。这是凭据用途限制，不是用户角色。
- 保持 HTTP 200 + `ResultModel.Code` 契约、密码校验与限流、改密吊销、刷新令牌轮换、脚本门禁/文件路径白名单、WS 鉴权不降级。
- 本次不引入多账号、团队、角色、ACL；不恢复已删除的脚本运行时或消息通道；不调整任务本身的启停、Cron、执行限额语义。

## 2. 现状与风险

| 位置 | 已核实行为 | 改造含义 |
|---|---|---|
| `LoginService.Login` / `AppAuthService.IssueAccessToken` | 同一配置账号登录，均签发 `Name`、`LoginTime`、`Manager=true`；App 另有 `DeviceId` | 新登录令牌保留主体与签发时间，停止签发角色 claim |
| `OpenAuthService.Auth` / `CustomAuthorizationFilter` | Open AppKey 也能换有效签名 JWT，`Name` 是固定标记；通用过滤器只验签 | 不能把“有效 JWT”直接视为登录用户 |
| `[ManagerOnly]` / `RealPrincipal` / `HttpContextExtension.IsManager` | 管理端点靠角色 claim；运行历史另挡 Open | 用统一的正向登录主体校验替换，覆盖端点与 WS |
| `TaskController` / `TaskService` | `Manager=false` 任务可被非 Manager 令牌列出和执行；管理操作另有 `[ManagerOnly]` | 移除角色字段前先阻断 Open 对登录任务端点的访问 |
| `TaskRunService` / `LogsService` | `ManagerSnapshot` 与日志目录参与历史可见性过滤 | 历史对唯一登录用户全量可见，Open 仍不可读 |
| `SystemConfigService.UpdatePassword` / `JwtTokenValidator.ValidateManagerNotBefore` | 改密靠 `Manager` claim 判断 access token 是否过期，App refresh 另行吊销 | 改为覆盖全部登录令牌，不能让旧令牌穿透 |
| App `TokenStoreApi` / `Stores` / `SessionManager` | 本地持久化 `isManager`，从 JWT claim 读取 | 删除持久化项和读写链；升级时忽略旧偏好键 |

`AGENTS.md` 指定的 `docs/security/公网部署安全审计-2026-09-14.md` 与 `docs/App端API契约.md` 在当前检出中缺失，不能声称已审阅。认证/任务/WS 正式改造前需取得可核验版本并核对本计划；若原件不可恢复，由所有者提供或确认新的等效安全基线与 App 契约。真实 `appsettings.json` 不进入计划、日志或测试数据。

## 3. 实施顺序

### 3.1 登录身份门禁先行

1. 在 `Quantum.Utils` 定义一种明确的登录令牌用途声明（如 `TokenPurpose=User`）；Web/App 两个签发入口都写入，Open 令牌保持独立用途，外部 PushKey/Secret 不作为登录 JWT。统一校验函数需先验签，再正向检查用途、非空 `Name`、与当前配置账号一致、有效 `LoginTime`；禁止配置账号名等于 Open 固定主体名。旧 Web/App access token 仅在原有效期内兼容：验签后满足当前账号名、`LoginTime`、且非 Open 固定主体；兼容判定不依赖 `Manager` 值。按当前实际签发路径和历史格式逐一测试，不接受只有 `Name` 的任意旧令牌。
2. 将 `[ManagerOnly]` 替换为表示“已登录用户”的过滤器；`RealPrincipal` 复用同一校验器，`CustomAuthorizationFilter` 仍负责统一验签。盘点每个控制器/动作的 `[AllowAnonymous]`、`[CustomAuthorizationFilter]`、原 `[ManagerOnly]` 组合，保证未登录与 Open 均返回 HTTP 200、信封 `Code=401`。`TaskController` 的列表、详情、执行、导入导出、步骤操作整体改为登录用户访问；不能仅删除过滤器。`AppWebSocketMiddleware` 的 URL 令牌握手和首帧 `auth` 两处均改为同一登录用途校验，Open 不得进入广播连接；核对媒体下载路径的令牌用途。
3. 将改密时间闸改为所有**登录** access token 的签发下限；兼容读取旧配置键 `ManagerTokenNotBefore`，写入新配置键前明确升级/回退的序列化口径，不能让旧值被默认 0 覆盖。App refresh token 继续同批吊销，设备解绑、刷新重放处置保持现有语义。新旧 Web/App access token、Open token 各测改密前后。

### 3.2 删除任务角色数据与服务分支

1. 移除 `TaskModel.Manager`、`TaskRunModel.ManagerSnapshot`、`TaskSaveModel.Manager` 等读写 DTO 与导入导出字段；任务、步骤、运行历史、日志服务改为单一登录用户视图，删除 `isManager`/`excludeManager` 参数和角色过滤。`TaskRunRecorder`/重试派生、`MessageProcess`/外触构造、AI 写工具及脚本安全扫描相关引用逐处核对，区分角色语义与名称里恰含 `Manager` 的无关类型。
2. 对 SQLite 与 MySQL 分别生成迁移，仅在所有读写代码不再使用字段后删除 `t_task.Manager` 和 `t_task_run.ManagerSnapshot`；核对两侧 Up/Down 一致、当前模型快照一致。字段删除属不可逆数据丢失，部署前备份；Down 仅能重建默认值，不能恢复历史角色位。新库 `EnsureCreated` 直接使用新模型，种子任务不写角色标记；旧导入文件里的 `Manager` 作为已废弃字段忽略，不得借导入扩大权限。
3. 登录用户可读全部历史任务/执行/日志，但 Open、PushKey 和回调仍受原用途限制。逐一核对 `TaskRunController`、`LogsController`、`AppMessageController`、`AppNotificationController`、`UploadController`、`AiAgentController`、`AiProviderController`、`ChannelController`、系统设置与设备接口；日志删除/清空等破坏性操作仍需登录身份。

### 3.3 Web、App、文档同步

1. Web 当前任务表单未查到角色选项；保持这一点，并移除运行策略的“仅管理员”文案/`canWritePolicy` 角色逻辑，登录/设置文案改为“账号”。核对路由和 API 封装不再把角色状态当作能力来源；保留服务端拒绝时的错误显示。
2. App 移除 `TokenStoreApi.isManager`、`Stores` 的 `IS_MANAGER` 键和 `SessionManager` 的 claim 解析，更新假存储与网络测试；任务 DTO 不再暴露 `Manager`。个人页/登录页/系统设置/日志页去掉角色徽章、角色限定文案和因此产生的显隐分支。现有 `feature:admin` 模块名可以内部保留到独立目录整理时再改，用户可见标题改为“设置”；不可为删除名称而扩大本次重构范围。
3. 更新 `AGENTS.md`、README、API 契约和运维文档里关于单用户、登录凭据与外部凭据的说明；保留必要的安全边界描述，清理“管理员/普通用户”产品用语。旧历史设计文档仅加现状说明，不批量篡改审计结论。

## 4. 测试与验收

| 层次 | 必须验证 |
|---|---|
| 后端鉴权 | Web/App 新令牌可访问全部登录功能；有效 Open 令牌不能读取/执行任务、脚本、环境变量、日志、AI、设备与系统设置；无/伪造/过期令牌均 `Code=401`；`AllowAnonymous`、PushKey、外触 Secret 仅能走各自端点 |
| 改密与兼容 | 改密后旧 Web/App access 和 refresh 令牌失效；老登录令牌只在原有效期内按明确主体规则兼容；旧 Open 令牌不会因无角色检查而升级；App 解绑/轮换/重放不回归 |
| 数据 | SQLite/MySQL 迁移 Up/Down、全新库建表和迁移历史、存量带两种 `Manager` 值的任务与运行记录、新旧任务 JSON 导入导出、日志详情与分页、种子任务均可验证 |
| 客户端 | Web `npm run test` + `npm run build`；App `testDebugUnitTest` + `assembleDebug`；浏览器与真机验证登录、设置、任务执行/历史/日志、扫码授权、改密重新登录、WS 通知；旧 App 与新服务端的过渡行为单独验收 |
| 项目门禁 | `dotnet build`、`dotnet test Quantum.API/Quantum.API.sln` 全绿；安全测试重点扩充 `SecurityHardeningTests`、`PermissionLayeringTests`、`TaskRunAuthorizationTests` 与新增登录用途测试 |

验收标准：应用里无角色选项/徽章/限定提示；唯一账号登录 Web/App 后任务和系统功能完整可用；Open/PushKey/Secret 无法取得登录能力；改密即时吊销登录凭据；双库新装与存量升级都能正常启动。不能以客户端隐藏入口替代服务端测试。

## 5. 部署、回退与工作量

1. 在隔离环境先备份数据库与配置，使用旧库副本演练双库迁移和旧客户端；核对安全审计/App 契约后再安排生产。不要读取或传播真实连接串/密钥。
2. 先发布含登录用途门禁和旧令牌兼容的新服务端，再同步 Web 静态资源与 App；确认没有仍依赖角色 claim 的旧客户端后停止签发旧 claim。正式删除字段的迁移与对应服务端版本同批发布，避免旧服务端读已删列。检查脚本目录与种子任务路径不会被发布脚本覆盖。
3. 回退优先恢复同一时间点的数据库与旧服务端，并保留 Web/App 旧构建；单独回滚二进制到会读取已删除列的版本不可行。令牌用途变化时要求重新登录，不把外部凭据转换成登录令牌。
4. 预计 8-13 人日（后端鉴权/数据 4-7，Web/App 与文档 2-3，双库及真机验证 2-3）；安全文档补齐、旧客户端兼容调查和真实环境迁移演练另计。无新增运行时依赖。

## 6. 实施前门禁

- 仓库所有者确认本计划的单用户边界与外部凭据用途边界。
- 取得并核对缺失的安全审计与 App API 契约，或由所有者提供等效现行版本；在此之前不改认证、WS 与脚本执行敏感链路。
- 核查是否有仍在线的旧 App 版本、外部调用方依赖任务查询/执行端点、以及旧 `Manager` 字段的导入文件；据此确定兼容窗口与发布时间。
