# 飞书消息通道接入计划（含飞书富文本方案探查）

> 编制日期：2026-09-27。范围：在既有「消息通道」体系（QQBot / WeixinBot）上新增 **飞书（FeishuBot）**，并探明飞书支持的富文本与「可点决策选项」方案。
> 状态：**待确认**。按仓库约定，本文档确认后再动手实施。
> 证据来源：飞书开放平台官方文档（文末列出）；仓库现状为 2026-09-27 `ChannelCore` 迁移后的代码实况。

## 0. 结论摘要

1. **形态选型：企业自建应用 + WebSocket 长连接**（不是群自定义机器人，也不是 Webhook 回调）。
   - 排除自定义机器人：**它发出的卡片只支持「按钮/文字链跳转 URL」，不支持点击回调**，且**根本收不到用户消息**（「自定义机器人能响应用户消息吗？不能」）——「双向 + 可点决策」两条都不成立。
   - 在「Webhook 回调」与「长连接」之间选长连接：长连接**同样支持新版卡片回调** `card.action.trigger`（官方 Python/Java/Node 样例均以 `lark.ws.Client` 注册；只有**旧版** `card.action.trigger_v1` 不支持长连接），因此决策选项不受影响；而它**不需要公网 IP / 备案域名 / 内网穿透**，只要求运行环境能出网。
   - 原先「无 C# SDK 需自研」的顾虑只对了一半：确实**没有官方 C# SDK**，但社区已有可用实现（见 §1.1）。
2. **富文本方案：交互卡片（`msg_type=interactive`，卡片 JSON 2.0）+ `lark_md` 富文本组件**。
   飞书三种消息类型里，只有卡片能同时满足「富文本 + 可点决策 + 点击回调 + 卡片可回写状态」。`post` 富文本消息连颜色都不支持，`text` 只有纯文本。
3. **「可点决策选项」= 卡片 `button` 组件 + `behaviors.type=callback`**，点击走 `card.action.trigger` 回调。
   官方 SDK **只支持对象类型的 `value`**，字符串型 `value` 不支持——这直接决定了本平台 payload 的形状（见 §2.4）。
4. **长连接的「3 秒」约束形态变了，内容不变**：Webhook 下是「3 秒内返回 HTTP 200 + 卡片 JSON」，长连接下是「3 秒内处理完并把响应**序列化成 protobuf 帧**回传」，超时触发飞书侧**超时重试**。因此决策抢占与卡片回写仍必须同步完成，重活一律转后台。
   （若最终回退到 Webhook 形态，`ResultFilter` 信封豁免问题才会出现：`url_verification` 要 1 秒内原样返回 challenge，而 `[ResultFilter]` 挂在 `BaseController` 上，回调端点只要不继承 `BaseController` 即天然豁免，过滤器本体无需改动。）
5. **决策选项需要能触发任务**（所有者裁决）。但**不新建执行旁路**：「点重跑」= 批准 G3 既有重试链的一次重试，由 `TaskRunService` 的轮询器自然派生，**免费继承脚本未变更、任务启用、重试上限、单活顺延四道护栏**。
   执行权由 `t_channel_binding.CanTriggerTask`（**默认 false**）显式授予，决策本身是「范围固定 + 一次 + 30 分钟过期」的一次性凭证；飞书点击**不签发任何 token、不产生 Manager claim**。详见 §3.3 与 §5。
6. **仅支持私聊，不支持群聊**（所有者裁决）。因此**不申请** `im:message.group_at_msg` 等任何群权限（少申请即少攻击面），入站显式拒绝 `chat_type != p2p`，`receive_id_type` 固定 `open_id`。现有「每平台唯一私聊绑定」模型原样成立，`t_channel_binding` 唯一索引无需放宽。

## 1. 飞书通道形态选型

| 维度 | A. 群自定义机器人（webhook） | B. 企业自建应用 + Webhook 回调 | **C. 企业自建应用 + 长连接（推荐）** |
|---|---|---|---|
| 接入成本 | 最低，贴 URL 即可 | 中：需公网地址 + 验签/解密 | **中：需建应用、申请权限、订阅事件、创建版本并发布** |
| 收用户消息 | ❌ 不能 | ✅ `im.message.receive_v1` | ✅ 同左 |
| 发卡片 | ✅ | ✅ | ✅ |
| **点击回调（决策选项）** | ❌ **明确不支持** | ✅ `card.action.trigger` | ✅ 同左（新版支持；**旧版 `card.action.trigger_v1` 不支持长连接**） |
| 公网入口 | 不需要 | **需要** | **不需要**（只需能出网） |
| 频控 | 单租户单机器人 100 次/分钟、5 次/秒 | 接口 1000 次/分钟、50 次/秒；对同一用户 5 QPS | 同 B |
| 请求体上限 | 20 KB | 文本 150 KB；卡片/富文本 30 KB | 同 B |
| 鉴权 | webhook URL + 可选 HMAC 签名 | `tenant_access_token` + Encrypt Key 验签 + AES 解密 | `tenant_access_token` + **建连时鉴权，之后明文推送** |
| 拿 open_id | ❌ 无数据访问权限 | ✅（需 `contact:user.id:readonly` 等） | 同 B |
| 3 秒约束的形态 | — | 3 秒内返回 HTTP 200 + 卡片 JSON | 3 秒内处理完并**回 protobuf 响应帧**，超时触发重试 |
| 与本仓库契合度 | 只能做单向推送 | 高（但要公网入口） | **高**：`ChannelNetwork.WebSocketInvoker` 已有现成 WS 通路；无公网依赖 |

**推荐 C**，理由：

- 唯一同时满足「双向 + 可点决策 + 免公网入口」三条件的形态。A 被「不能收消息 + 无卡片回调」双重排除；B 与 C 在功能上对等，差别只在**是否需要公网入口**。
- 本仓库的部署形态偏内网（`docs/执行记录与外部推送API契约.md` 提到生产库在 NAS），若实例没有稳定公网入口，B 直接不成立。
- C 的「集群模式不广播」在本仓库不构成新约束——仓库已明确**单实例部署**（同上文档 §7「不得横向扩容调度节点」）。
- C 省掉了一整条安全链路：不用维护 Encrypt Key 验签、AES 解密、回调端点匿名可达面、IP 限流与 XFF 可信口径。

**代价（须一并接受）**：

- 多一个常驻长连接与重连/保活逻辑（Ping/Pong、断线指数退避、超大事件拆包合包）。
- 依赖社区库（§1.1），存在供应链与维护风险。
- 决策响应要以 protobuf 帧回传，不是 HTTP body，调试链路与 Webhook 形态不同。

### 🔴 1.0.5 必须在编码前解决的冲突：长连接到底收不收得到卡片回调

本轮核实发现**两个来源直接矛盾**，而这条恰好是「可点决策选项」能否成立的前提：

| 来源 | 结论 |
|---|---|
| **飞书官方文档**（Python/Java/Node 三语言样例） | 用 `lark.ws.Client` 注册 `register_p2_card_action_trigger`，**长连接支持卡片回调**。且「消息卡片回传交互(**旧**)」不支持长连接——反证新版支持 |
| **第三方 Skill 文档**（lobehub，标注 2026-02-10） | 「**WebSocket currently does NOT subscribe to card.action.trigger events. Buttons on cards are display-only for now.**」并建议改用「回复文字」的降级方案 |

**可能的解释**（都未证实）：

1. 第三方作者用的是**旧版卡片**（`card.action.trigger_v1`），撞上了旧回调不支持长连接的限制；
2. 2026-02-10 之后飞书补上了能力（官方文档更新更晚）；
3. 存在版本/权限差异（如需在后台额外订阅卡片回传交互）。

**处置**（已写入 §6 前置验证，**这是接入前必须跑通的第二步**）：

- 最小样例里**必须包含**：点一次卡片按钮，确认长连接收到 `card.action.trigger`。
- **若实测不通**：决策选项**不能**走长连接，此时二选一——
  - (a) 该通道退回 **B（Webhook 回调）**，仅此一个端点需要公网地址，事件主体仍走长连接；
  - (b) 决策选项降级为**文字指令**（用户回复「重跑 1234」），牺牲点击体验换取免公网依赖。
- **不接受**的做法：先按能收到写完 P1，最后才发现回调不通。

### 1.1 长连接协议与 C# 生态（本轮新增核实）

**协议要点**（据官方文档与社区实现一致描述）：

| 环节 | 内容 |
|---|---|
| 取接入地址 | `POST /callback/ws/endpoint`。**请求体字段名大小写敏感，只认 `AppID`/`AppSecret`**——写成 `appId`/`app_id` 一律 `HTTP 400 + code=9499 Bad Request`（此处曾造成本通道「扫码成功但永远连不上」）。成功响应把地址**嵌在 `data` 里**：`{"code":0,"data":{"URL":"wss://…","ClientConfig":{…}}}`，`ClientConfig` 含 `PingInterval`/`ReconnectInterval`/`ReconnectCount`/`ReconnectNonce`，**服务端下发、动态覆盖本地默认**。以上为 2026-09-28 真实凭据实测结果 |
| 传输 | `ClientWebSocket`（BCL 内置）连飞书 wss 地址，收发**私有 protobuf 二进制帧（`pbbp2`）** |
| 帧结构 | 字段序：`1 SeqID` varint、`2 LogID` varint、`3 service` varint（Ping 帧用）、`4 method` varint（0=控制帧 / 1=数据帧）、`5 headers`（多个 `Header{key,value}`）、`6 payload_encoding`、`7 payload_type`、`8 payload` bytes、`9 LogIDNew` |
| 事件体 | v2 envelope：`{schema:"2.0", header:{event_id,event_type,create_time,app_id,tenant_key}, event:{…}}` |
| 保活/重连 | 定时 Ping/Pong；断线指数退避 + 抖动 + 次数上限；超大事件自动拆包合包 |
| 限制 | 每应用最多 50 连接；集群模式不广播；3 秒处理时限。**「仅企业自建应用」已由 2026-09-28 实测推翻**：扫码注册出的 PersonalAgent 个人应用同样取得到 wss 地址、握手 `State=Open` |

**C# 可选实现**（两者均为社区库，**飞书官方不提供 .NET SDK**）：

| 包 | 许可/版本 | 特点 | 适配本项目的风险点 |
|---|---|---|---|
| `FeishuWss` | MIT，.NET 8/9/10 | **手写 protobuf wire-format**，不引 protobuf 依赖；仅依赖 `Microsoft.Extensions.Logging.Abstractions`；`ClientWebSocket` 用 BCL | **下载量极小（约 88）**、单人维护；其 README 自述「当前分发器只路由 event 帧，card 帧入口已预留，卡片回调可用 `OnCustomizedEvent("card.action.trigger", …)` 透传」——**决策选项需走透传而非强类型**；仅内置 `im.message.receive_v1` 一个强类型事件 |
| `FeishuNetSdk`（+ `.WebSocket` / `.Endpoint`） | .NET 8 | 更成熟的 API 封装与 DI 集成，含 webhook 端点扩展 | 引入 `WebApiClientCore` 2.1.5 等传递依赖；体量与攻击面更大 |

> ⚠️ **供应链风险须走仓库既有流程**：`AGENTS.md` 记录本机 NuGet 源偶发拉取失败，且仓库对新增依赖一贯谨慎。两个包都不是官方维护。**所有者已裁决：接受引入非官方社区包。**
>
> **据此本计划推荐 `FeishuWss`**，理由：MIT 许可、**只依赖 `Microsoft.Extensions.Logging.Abstractions`**（无 `WebApiClientCore` 等传递依赖，攻击面最小）、手写 wire-format 反而便于加帧编解码回归测试。
> 其「卡片回调走 `OnCustomizedEvent("card.action.trigger")` 透传」**对本项目不构成障碍**——决策回调我们本来就要自己解析 JSON 并做条件 UPDATE 抢占，不需要 SDK 的强类型封装。
> `FeishuNetSdk` 保留为备选（若 `FeishuWss` 样例跑不通，它的长连接实现更成熟）。
> **无论选哪个：锁定版本、记录来源，且必须先过 §6 的最小样例验证。**

### 1.2 回退方案

若长连接的依赖评审不通过或样例验证失败，回退到 **B（Webhook 回调）**——功能完全对等，只是需要公网入口，且要额外处理 §5 的信封豁免与验签链路。**两个形态共用同一套 inbox/outbox/绑定/决策数据模型**，切换只影响「事件入口」这一个适配层，不影响其余设计。

> **前置代价（必须提前知道）**：飞书权限、事件订阅、可用范围三件套**保存 ≠ 生效，必须「创建版本 → 发布」**。只保存不发布的表现是「连接正常、日志无错、消息静默丢弃」，排查成本很高。实施时须把这条写进运维手册。

## 2. 飞书富文本方案探查

### 2.1 三种消息类型能力对比

| 能力 | `text` 文本 | `post` 富文本 | **`interactive` 卡片（JSON 2.0）** |
|---|---|---|---|
| 粗体 / 斜体 / 删除线 | ❌ | ✅（元素 `style`） | ✅ `lark_md` |
| 超链接 | ❌ | ✅ 元素 `a` | ✅ `[文字](url)` |
| 文字颜色 | ❌ | ❌ | ✅ `lark_md` 彩色文本 / `plain_text.text_color` |
| 标题 / 引用 / 分割线 | ❌ | ❌ | ✅（`markdown` 组件，**仅 2.0 结构**） |
| 表格 | ❌ | ❌ | ✅（**仅 2.0 结构**，`table` 组件） |
| 有序 / 无序列表 / 代码块 | ❌ | ❌ | ✅（仅 2.0 结构） |
| 行内图片 | ❌ | ✅ 元素 `img` | ✅（`markdown` 组件，**需先上传取 `image_key`**） |
| **可点按钮** | ❌ | ❌ | ✅ `button` |
| **点击回传服务端** | ❌ | ❌ | ✅ `behaviors.type=callback` → `card.action.trigger` |
| 卡片状态回写 | ❌ | ❌ | ✅ 回调内直接返回新卡片，或 30 分钟内延时更新 |
| `@ 人` | ✅ `<at user_id>` | ✅ 元素 `at` | ✅ `<at id=all></at>` |
| 体积上限 | 150 KB | 30 KB | 30 KB |

**结论**：本平台的富文本一律走卡片，`post`/`text` 只作为降级路径（§2.5 末）。

### 2.2 卡片 JSON 2.0 组件矩阵（与本需求相关的部分）

| 组件 `tag` | 用途 | 本期用否 |
|---|---|---|
| `markdown` | 富文本（Markdown 语法子集） | ✅ **主力** |
| `plain_text` | 纯文本，可设 `text_color`/`text_align`/`lines`/`text_size`/前缀图标 | ✅ |
| `div` | 文本容器（内含 `plain_text` 或 `lark_md`） | ✅ |
| `hr` | 分割线 | ✅ |
| `img` | 图片（`img_key`，需先上传） | ⏸ 二期 |
| `column_set` / `column` | 分栏布局 | ⏸ 二期 |
| `note` | 脚注 | ✅ 承载降级提示 |
| **`button`** | **按钮：`behaviors` 决定行为** | ✅ **决策选项载体** |
| `overflow` | 更多菜单 | ⏸ |
| `form` + `select_static` / `multi_select_static` / `check_box` / `text_input` / `date_picker` / `person` | 表单容器，提交回传 `form_value` | ⏸ P2 |
| `collapsible_panel` | 折叠面板 | ⏸ P2 |
| 表格 / 图表 | `table` / `chart` | ⏸ P2 |

> **另有两个「非组件」的富文本内联标签，本项目要用**：
> - **`<text_tag color='X'>文字</text_tag>`** —— **飞书原生胶囊标签**（官方 column_set 示例大量使用），是 `{{tag:}}` 的精确落点，不需要用 `column_set` 色块模拟。
> - `<font color='X'>文字</font>` —— 彩色文字；`grey` 在官方示例中确实可用。
> - `header.text_tag_list` —— 标题后缀标签（**上限 3 个**），属卡片结构字段而非组件。

约束：JSON 2.0 卡片**组件/元素总数 ≤ 200**（超限报 `11310`）；卡片体积 **≤ 30 KB**；`element_id` 字母数字下划线、字母开头、≤20 字符且卡内全局唯一。

### 2.3 `lark_md` 支持的 Markdown 语法（真实支持矩阵）

| 能力 | 语法 | 可用范围 |
|---|---|---|
| 换行 | `\n` | 全部 |
| 斜体 | `*斜体*` | 全部 |
| 粗体 | `**粗体**` / `__粗体__` | 全部 |
| 删除线 | `~~删除线~~` | 全部 |
| 文字链接 | `[文字](https://…)` | 全部，**必须带 scheme**（仅 http/https 生效） |
| 超链接 | `https://…` | 全部 |
| @ 人 | `<at id=ou_xxx></at>`、`<at id=all></at>` | 全部（@所有人需群开启权限，否则**整条卡片发送失败**） |
| 彩色文本 | `<font color='red'>红色</font>` | 全部 |
| emoji | `😁😢🏆❌✅` | 全部 |
| 飞书表情 | `:OK:` | 全部 |
| 标签 | `neutral` | 全部 |
| 分割线 | `\n---\n` | ⚠️ **仅 `markdown` 组件，`lark_md` 类型的 `text` 元素不支持** |
| 行内图片 | `![](img_key)` | ⚠️ **同上，仅 `markdown` 组件支持** |
| 标题 / 引用 / 行内引用 / 表格 / 有序列表 | `#`、`>` 等 | ⚠️ **仅卡片 JSON 2.0 结构支持**（1.0 不支持） |

**颜色枚举**（本轮已从官方 JSON 2.0 结构文档确认，**分三套、互不相同，实施时勿混用**）：

| 用途 | 可用值 |
|---|---|
| `<font color>` 彩色文字 | 2.0 枚举：`neutral/blue/turquoise/lime/orange/violet/indigo/wathet/green/yellow/red/purple/carmine`，**外加官方示例中实际使用的 `grey`** |
| `<text_tag color>` 胶囊标签 | 2.0 枚举同上（**不含 `grey`**，灰色标签用 `neutral`） |
| `header.template` 标题主题 | `blue/wathet/turquoise/green/yellow/orange/red/carmine/violet/purple/indigo/grey/default` |
| `background_style` / 自定义色 | 上述枚举 **+ RGBA 自定义色**（`config.style.color_v2` 可定义 `light_mode`/`dark_mode` 两套） |

字号：`text_size` 支持 `heading-0`(30px) ~ `notation`(12px) 等档位，并可在 `config.style.text_size` 自定义**移动端/桌面端分别**的字号。

### 2.4 「可点决策选项」方案（三档，按能力递进）

#### 档 1：按钮 + 回调（**本期主方案**）

```jsonc
{
  "schema": "2.0",
  "config": { "update_multi": true },
  "header": { "title": { "tag": "plain_text", "content": "任务失败：什么值得买" }, "template": "red" },
  "body": { "elements": [
    { "tag": "markdown", "content": "**连续失败 3 次**\n最后一次：`ScriptException`\n[查看执行记录](https://…)" },
    { "tag": "button", "text": { "tag": "plain_text", "content": "重跑一次" },
      "type": "primary", "behaviors": [
        { "type": "callback", "value": { "d": "<决策Id>", "k": "retry" } }   // 必须是对象
      ] },
    { "tag": "button", "text": { "tag": "plain_text", "content": "忽略本次" }, "type": "danger",
      "behaviors": [ { "type": "callback", "value": { "d": "<决策Id>", "k": "ignore" } } ] }
  ] }
}
```

回调 `card.action.trigger` 关键字段：

| 字段 | 说明 |
|---|---|
| `event.operator.open_id` | 点击者 |
| `event.action.value` | **开发者自定义对象**（与按钮 `behaviors.value` 一一对应） |
| `event.action.tag` / `event.action.name` | 交互组件类型与名字 |
| `event.token` | **卡片更新凭证：30 分钟内有效，同一 token 最多更新 2 次** |
| `event.context.open_message_id` / `open_chat_id` | 卡片所在消息与会话 |
| `event.action.form_value` | 表单容器提交值（本期不用） |

**硬约束**：

- `behaviors.value` **必须为对象**——官方 SDK 仅支持对象类型，字符串型不被支持。
- 必须在 **3 秒内**给出响应，否则飞书客户端展示报错、并触发超时重试。
  - **Webhook 形态**：返回 HTTP 200 + 卡片 JSON（或 `{}` 表示稍后更新）。
  - **长连接形态（本期选定）**：把响应**序列化为 protobuf 响应帧**经同一条连接回传。约束内容相同，载体不同。
- 回调是**同步操作**：超时不响应即判失败。**Webhook 下无补推机制**；长连接下会触发重试，因此两种形态都必须保证「3 秒内必有响应」，且**重活一律转后台**。
- 幂等：按 `value` 里的决策 Id 走**条件 UPDATE 抢占**（`WHERE Status='Open'`），影响 0 行即返回「该决策已处理」的 toast。重试导致的重复回调由这条闸门吸收。

**卡片回写两条路**：

| 方式 | 做法 | 上限 | 适用 |
|---|---|---|---|
| 回调内即时回写（**默认**） | 3 秒内直接返回新卡片 JSON（不需最外层 `card` 壳） | 无限次，但须发得出去 | 决策结果立刻可见 |
| 延时更新 | 先返回 `{}`，再用 `event.token` 调延时更新 | **30 分钟、同一 token 最多 2 次** | 需异步查证的决策 |
| 按 message_id 更新 | `PATCH /im/v1/messages/{message_id}` | 14 天内、5 QPS、须 `update_multi=true` | 业务侧主动改卡片（超时兜底） |

#### 档 2：表单容器（`form` + `select_static` / `check_box` / `text_input`）
一次提交收多个字段（如「原因下拉 + 备注」），值走 `form_value`。适合**结构化问卷**，不适合「同意/拒绝」二选一。

#### 档 3：下拉选择器（`select_static` / `multi_select_static` / `check_box`）
选项多于 4~5 个时比横排按钮好看，但交互深度多一步。

**本期只做档 1。** 档 2/3 列入 P2。

## 3. 与现有通道架构的契合与改造点

### 3.1 可直接复用（改动小）

现有骨架对飞书几乎完全适用：

- `t_channel_account` / `t_channel_binding` / `t_channel_inbox` / `t_channel_outbox` / `t_channel_reply_route` / `t_channel_allowed_command` 六张表**无需改结构**（`Platform` 列 `nvarchar(16)` 装得下 `FeishuBot`）。
- **绑定挑战**：`ChannelInboxService` 的 `ObserveChallengeAsync` 已是平台无关实现，飞书复用「Manager 在私聊里发 6 位挑战码 → 事件带 `open_id` → 候选 → Manager 二次确认」，与 QQ 完全同构。
- **入站事务**：`AcceptBatchAsync` 的「整批成功才推进、失败绝不推进」语义对飞书同样正确（飞书 `message_id` 去重，不依赖 `event_id`）。
- **私聊假设原样成立**：现有模型已是「每平台唯一私聊绑定」，而本期**只做私聊**（所有者裁决不支持群聊），所以 `t_channel_binding` 的唯一索引、绑定挑战、权限收敛全部不用动。群聊会打破「唯一绑定」假设并需要 `chat_id` 维度的多绑定，属独立议题。
- **原路回复**：`t_channel_reply_route` 的 `ReplyMessageId` 直接存飞书 `message_id`，走 `POST /im/v1/messages/{message_id}/reply`，天然是「原路」。
- **投递账本**：`ChannelDeliveryWorker` 的单活 Claim + 绑定版本检查 + `Unknown` 不自动重发，直接套用。
- **快捷回复**：`ChannelQuickReplyService` 的「仅 Manager 显式勾选的纯文本命令」模型不变。

### 3.3 新增数据模型

**所有者已裁决：决策选项需要能触发任务。** 这推翻了首轮「只记账、不执行」的设计，下面的授权模型是本计划**最敏感的部分**。

```
t_channel_decision（新增，决策卡片账本 = 一次性执行授权凭证）
  Id                    对外决策 Id（RandomNumberGenerator 32 hex，不可枚举）
  AccountId / PeerId / BindingVersion
  OutboxId              来源投递记录（唯一索引）
  MessageId             飞书卡片消息 Id（om_xxx）
  Kind                  RetryRun（批准一次重试）/ RunNow（立即执行）/ Approve（仅记账）
  TaskId                目标任务（Kind 为执行类时必填）
  RunId                 目标执行记录（Kind=RetryRun 时必填）
  OptionsJson           [{Key,Label,Style}]，≤ 5
  ExpiresAtUtc          决策有效期（**默认 30 分钟，不是 24 小时**）
  Status                Open / Applied / Ignored / Expired / Cancelled / Failed
  AnsweredKey           被点中的选项
  AnsweredBy            点击者 open_id（不写进日志，仅落库供审计）
  AnsweredAtUtc
  ResultRunId           执行后派生出的新 RunId（回写卡片用）
  ResultCode            执行结论（受理成功 / 被拒原因码）
  TokenCiphertext       30 分钟更新 token 的密文（过期后清空）

t_channel_binding（既有表，新增一列）
  CanTriggerTask        bool，默认 false —— Manager 在确认绑定时显式勾选
```

**授权模型（三层，缺一不可）**：

1. **谁在点**：`event.operator.open_id` 必须等于 `t_channel_binding.PeerId`（每平台唯一绑定，由 Manager 走挑战流程显式确认过）。不对则拒收并留痕。
2. **能不能点**：`binding.CanTriggerTask == true`。**默认 false**——授权由 Manager 在受控端显式授予，可随时改回 false 立即收回。不把「绑定了飞书」等同于「可以执行任务」。
3. **能点什么**：决策记录自带 `TaskId` + `RunId` + `ExpiresAtUtc`。**它不是通用执行权，而是一张范围固定、只能消费一次、30 分钟过期的凭证**。卡片上的按钮只能对这一个决策表态，不能指定别的任务。

> 关键取舍：**自动推送的告警卡片默认只读**，不含执行按钮。只有在 `CanTriggerTask=true` 时，失败告警才带「重跑本次 / 忽略」两个按钮。这样「飞书能触发任务」这件事本身是一个**可审计、可关闭、默认关闭**的配置，而不是通道的固有属性。

**`Kind=RetryRun` 的执行链（首期主推，最安全）**：

点「重跑」**不新建执行旁路**，而是给那条已终态失败的 run 重新设置 `NextAttemptAtUtc`，由既有 `TaskRunService.ClaimDueRetriesAsync` 轮询器自然派生一次新尝试。这样免费继承 G3 已有的全部护栏：

| 护栏 | 复用点 |
|---|---|
| 脚本已变更 → 拒绝执行 | `ApplyPolicyAfterTerminalAsync` 的 `ScriptFileSnapshot` 比对（`TaskRunService.cs:192`） |
| 任务已禁用/已删除 → 拒绝 | 同上 `:183-191` |
| 重试次数上限 | 同上 `:173-180`（`attemptsSoFar > policy.RetryCount` 即封顶） |
| 同任务已有非终态 → 顺延，不并发跑 | `DeferOrAbandonAsync`（累计 20 次后放弃并记 `CancelReason`） |
| 幂等与时序 | 条件 UPDATE 抢占（`TaskRunService.cs:268-274` 同款 `ExecuteUpdate` 模式） |
| 统一审计 | 派生出的尝试天然落在同一条 `t_task_run` 时间轴上 |

**因此 `Kind=RunNow`（立即跑一次全新执行）不放在首期**：它会创建新 `RootRunId`、绕开上述全部重试链约束，语义上等同「从聊天软件远程手动执行任意任务」，是本方案里风险最高的一条。留到 P2，届时需单独评审。

**为此需要的既有代码改造**：`ApplyPolicyAfterTerminalAsync` 目前是 private 且耦合在 `CompleteAsync` 内（`TaskRunService.cs:157`）。需将其校验段**抽为共用私有方法**，另暴露一个 public `ScheduleManualRetryAsync(runId, operatorName)` 供决策链调用——**复用同一份校验逻辑，禁止复制第二份**，否则两处必然漂移。

> 决策结果仍**不落 `t_channel_allowed_command` 体系**（那是纯文本快捷回复，与执行无关）。决策的执行动作直接落到 `t_task_run` 重试链，并追加一条会话消息（`ChatMessageDirection.发送`，含选项、点击者脱敏指纹、`ResultRunId`）供 Manager 事后核对。

## 5. 安全与红线

### 选长连接后，本节原本最大的两条负担直接消失

- **不再需要 `url_verification` 探测与 1 秒 challenge 响应**——没有回调地址就没有这条协议。
- **不再需要 Encrypt Key 验签、AES 解密、回调端点匿名可达面、来源 IP 限流与 XFF 可信口径**——长连接在建连时完成鉴权，之后推送为明文。
- 连带地，**`ResultModel` 信封豁免问题也不存在了**（没有 HTTP 回调端点）。若将来回退到 Webhook 形态，才需要处理这一条：`[ResultFilter]` 挂在 `BaseController`（`Quantum.Web/Controllers/BaseController.cs` 第 12 行）上、**是按控制器特性而非全局过滤器**（`EnumController : ControllerBase` 需自行显式标注即为证据），因此回调端点不继承 `BaseController` 即天然豁免，`ResultFilter` 本体一行不改，先例见 `AppMediaController`。

### 决策触发任务：授权边界（所有者已裁决「需要触发任务」，本节为最高风险区）

- **默认关闭**：`CanTriggerTask` 默认 `false`。不勾选时飞书只能收到只读告警，**一个字节的执行权都没有**。这符合仓库「新功能默认关闭」的既有惯例。
- **授权可即时收回**：Manager 把 `CanTriggerTask` 改回 false 即刻生效；解绑/换绑时一并作废全部 `Open` 决策（对齐 `RevokeAsync` 原子吊销语义），**不能让旧卡片在换绑后仍能执行**。
- **凭证最小化**：决策不是通用执行权，只对 `TaskId` + `RunId` 生效、只消费一次、**30 分钟过期**。卡片按钮无法指定其他任务，猜不出决策 Id（32 hex 随机）。
- **不产生身份**：飞书点击**不签发任何 token、不写 `Manager` claim**，不进入 `IsManager` 判定链。它只是消费一张预先由 Manager 授权的凭证——与「外部消息不得取得 Manager 身份」不冲突，但这条边界必须在代码注释里写死。
- **必须复用 G3 护栏**：`RetryRun` 走 `ScheduleManualRetryAsync`，与自动重试**共用同一份校验**（脚本未变更、任务启用、重试上限、单活顺延）。**严禁为决策另写一份执行入口**——那会绕过全部护栏，等于开一个后门。
- **只读失败信息**：卡片里不得出现环境变量、令牌、脚本正文；失败原因只给受控枚举（`ResultCode`），不把 `SafeSummary` 原文塞进 toast。
- **审计**：每次点击（无论成功/被拒）都留一行——`t_channel_decision` 状态流转 + 追加会话消息（脱敏指纹 + `ResultRunId`）。`AnsweredBy` 只落库不进日志。
- **`RunNow` 不进首期**：从聊天软件远程发起一次全新任务执行绕开了上述全部重试链约束，风险显著高于「批准一次重试」，留 P2 单独评审。

### 新增的红线（长连接形态特有）

- **凭据面收窄**：飞书账户只存 `AppId`/`AppSecret`，不落 EncryptKey/VerificationToken（回退形态需要时再补），继续走 `ChannelSecretProtector` 密文，DTO 一律回掩码。
- **依赖供应链**：`FeishuWss` / `FeishuNetSdk` 均为社区包、非官方维护。须先做最小样例验证（见 §6）再接入，锁定版本并记录来源；不接受「顺手加个包」式引入。
- **单实例约束**：长连接是集群模式不广播，多副本只会随机一个收到。本仓库已约束单实例，**不得因飞书而放开横向扩容**。
- **连接生命周期**：账户禁用/解绑必须立即断开长连接并停止重连（对齐 `RevokeAsync` 语义），否则会出现「已解绑但事件仍在进」的窗口。
- 事件处理异常**不得抛出到连接层**——飞书侧会因 3 秒超时触发重试，异常外溢会放大成重复投递。

### 沿用的既有红线

- 回调端点必须限流（按来源 IP + `app_id`），防探测打爆。
- `event_id` **不用于幂等**（官方明示可能重复推送），一律按 `message_id` 去重，复用 `t_channel_inbox` 现有唯一判定。
- 点击者身份以 `event.operator.open_id` 为准，必须与已绑定 `PeerId` 一致，否则拒收并留痕（不记录 open_id 原文到日志）。
- 决策 Id 用随机串，不自增、不含时间戳，避免被遍历猜中。
- 卡片内不放环境变量、令牌、脚本正文；任务摘要沿用既有 `SafeSummary`（≤512 字符、已脱敏）口径。
- 注意 `230028`：**明文手机号/邮箱会导致整条消息发送失败**——任务摘要里若有此类信息须在渲染前脱敏。
- 换绑沿用既有口径：改凭据必须显式确认，原子吊销旧绑定/路由/待发消息。

## 8. 扫码绑定增补（2026-09-27，已实施）

**需求**：飞书私聊的接入绑定改为**扫码完成**（参照 TerminalBuddy 的设备码授权实现），替代「管理员手动建应用 + 手填 AppId/AppSecret」的第一步；原有「候选 + Manager 二次确认」语义不变。

### 8.1 机制（飞书设备码授权注册流程）

协议端点：`POST https://accounts.feishu.cn/oauth/v1/app/registration`（form-urlencoded，三步）：

| 步骤 | 参数 | 返回 |
|---|---|---|
| `action=init` | 无 | `supported_auth_methods` 须含 `client_secret` |
| `action=begin` | `archetype=PersonalAgent`、`auth_method=client_secret`、`request_user_info=open_id` | `device_code`、`verification_uri_complete`（渲染成二维码）、`interval`、`expire_in` |
| `action=poll` | `device_code`、`tp=ob_app` | 成功：`client_id` + `client_secret` + `user_info.open_id`（扫码人）；等待：4xx + JSON `error=authorization_pending`；终态：`access_denied` / `expired_token` |

用户用**飞书 App** 扫码并确认后，飞书在扫码人账号下**自动创建个人应用机器人**，一次扫码同时拿到应用凭据与扫码人 open_id——无需去开放平台手动创建应用。注意：等待态返回 4xx 但 body 仍是 JSON，`ChannelNetwork.SendAsync` 因此增加 `readErrorBody` 能力（错误状态也解析 JSON body，body 非 JSON 再按状态码上报），表单编码经新增的 `PostFormAsync`（`accounts.feishu.cn` 本就在 `*.feishu.cn` 白名单与公网 DNS 校验覆盖内）。

### 8.2 实现落点与安全边界

- **`FeishuQrLoginService`**（单例状态机，同微信 `WeixinQrLoginService`）：`StartAsync`（校验主密钥可用、已配置/已绑定时须显式 `ConfirmRebind` 且先解绑旧配置，再 init/begin）→ `PollAsync`（成功即经 `ChannelManagementService.RegisterFeishuScanAsync` 加密落库并登记候选）。`device_code` 只存内存随会话失效，AppSecret 不回传前端、不写日志。
- **`ChannelManagementService.RegisterFeishuScanAsync`**：凭据按 `feishu-credentials` purpose 加密（与手填 `ConfigureFeishuAsync` 同形态）；扫码人 open_id 直接成为 `CandidatePeerId`；**平台未返回 open_id 时退回一次性挑战码**（与微信扫码无用户 ID 的回退一致）。Manager 仍须在管理页核对脱敏候选 + 指纹后「确认绑定」，且确认后通道保持关闭、需显式启用——§5 全部红线不变。
- **端点**（均 ManagerOnly）：`POST /api/Channel/feishu/qr/start`（审计）、`POST /api/Channel/feishu/qr/status`（轮询不审计）。
- **前端**：渠道页飞书卡片新增「扫码绑定」主按钮 + 扫码弹窗（`n-qr-code` 渲染、按 `interval` 轮询、失败/过期/拒绝提示、挑战码回退展示）；「配置应用」与「发起绑定挑战」保留为手动路径。
- **测试**：`FeishuQrScanTests`（poll/begin/init 解析、凭据加密不泄漏、候选登记→确认→启用、无 open_id 挑战回退与防重放、重扫码废止旧绑定与待发消息、入参校验）。

### 2026-09-27 第二轮审核（选型复议：长连接 vs Webhook）

**触发**：所有者指出「飞书支持 WebSocket 长连接，这样就不需要公网 IP」，质疑首轮推荐 Webhook 回调的结论。

**结论**：**首轮选型结论错误，已改**。长连接升为主选型。核实结果如下。

| 编号 | 级别 | 位置 | 问题与建议 | 状态 |
|---|---|---|---|---|
| R-FS-08 | 🔴 阻塞（已消解为待验证） | §1、§6 | **长连接引入非官方社区包，构成供应链风险。** 核实：飞书官方确无 .NET SDK（Go/Python/Java/Node 有），但社区已有两个可用实现——`FeishuWss`（MIT、.NET 8/9/10、手写 protobuf wire-format、仅依赖 `Microsoft.Extensions.Logging.Abstractions`、**下载量约 88**、README 自述卡片回调走 `OnCustomizedEvent("card.action.trigger")` 透传、仅内置 `im.message.receive_v1` 强类型）与 `FeishuNetSdk`（.NET 8、更成熟、引入 `WebApiClientCore` 2.1.5 等传递依赖）。建议：接入前必须先跑「最小样例验证」三步（建连 → 收 `im.message.receive_v1` → 收 `card.action.trigger` 并回帧），并由所有者拍板是否接受非官方依赖。 | **已写入计划（§1.1 依赖表 + §6 前置验证 + §7-1 决策点）** |

**首轮结论被推翻的原因（留档）**：

- 首轮写「飞书官方 SDK 无 C# 版本，长连接帧为 Protobuf 编码，需自行实现」——**前半句对、后半句下结论过早**。当时未核实 C# 生态是否存在现成实现，核实后确认已有可用社区实现，因此「自研成本高」这一否决理由不成立。
- 首轮未意识到**新版 `card.action.trigger` 支持长连接**（只有旧版 `card.action.trigger_v1` 不支持），误以为长连接会牺牲决策选项能力。官方 Python/Java/Node 样例均以 `lark.ws.Client` 注册该回调，可证。
- 连带修正：长连接下 §5 原先的头号负担（`ResultFilter` 信封豁免、Encrypt Key 验签、AES 解密、匿名可达面、IP 限流与 XFF 口径）**全部消失**。

**长连接带来的新风险（已登记进计划 §5）**：集群模式不广播（但仓库已单实例约束，不构成新约束）；连接生命周期须与解绑/禁用联动；事件处理异常不得外溢到连接层否则触发飞书侧重试；断线重连与保活需专门测试。
